3.2Where score actually comes from (first principles)

Solving a task = generating a candidate program/rule whose execution on the test input reproduces the ground truth, then selecting the right 2 candidates from everything generated. Every historical gain decomposes into these levers:

LeverWhat it isWhy it exists / why it worksEvidence status
L1 · Priors (generation)Models pretrained on ARC-like data (synthetic corpora, prior-year tasks) that emit plausible transformations in-context or as code.ARC rewards fluent skill acquisition; priors shrink the hypothesis space a priori.FACT every top system since 2024 uses strong priors.
L2 · SearchProgram search: DSL enumeration, evolutionary mutation with execution feedback, beam over program space.Execution-verified search converts compute into exactness; LLM guidance makes it tractable.FACT 2024 top-5 (DSL/program search); SOAR (2025 paper 2nd).
L3 · Selection & verificationRank candidates by train-fit, execution consistency, augmentation agreement; choose attempt_1/attempt_2.Pass@2 means selection quality caps everything: a 40% pass@8 pool is worthless if your top-2 picks are wrong.HYPOTHESIS biggest under-exploited lever for us — measure first (C2-E04→E07).
L4 · Test-time training/adaptationPer-task fine-tuning on augmented demonstration pairs; select checkpoint by train fit.Specializes priors to each task's rule family; the single biggest 2024 breakthrough.FACT Akyürek et al.; ARChitects; MindsAI; NVARC all use variants.
L5 · Ensembling (diversity)Union/voting across heterogeneous solver families (TTT net, TRM-class, program search, MDL).Different families fail on different task types; NVARC's 24% came from stacking unlike components.FACT NVARC; ARChitects soft-voting; Product-of-Experts paper.
L6 · Compute allocationEarly-exit solved tasks; difficulty triage; adaptive k per task; batching; cache.12h hard cap: wasted GPU-minutes on solved/unsolvable tasks are stolen from unsolved ones.OBSERVATION common postmortem theme; big cheap wins.
L7 · Data engineeringSynthetic generators targeted at AGI-2 axes: symbolic interpretation, compositional rules, contextual rules.Train distribution ≠ eval distribution; targeted synthesis closes the specific gap AGI-2 was designed to create.HYPOTHESIS NVARC credits synthetic data; exact recipe = their edge.
Why ARC-AGI-2 is structurally different from ARC-AGI-1 FACT (arcprize.org capability tests): ① symbolic interpretation — symbols carry meaning beyond visual pattern; ② compositional reasoning — multiple interacting rules applied simultaneously; ③ contextual rule application — same rule applies differently by context. Systems that pattern-match AGI-1 transformations stall here; that stall is exactly the gap our data (L7) and selection (L3) should attack. Reasoning-model baselines score near 0–8% (FACT TRM ~8% AGI-2; CompressARC ~4%), while the calibrated evals remain human-solvable pass@2 by design.

3.4Strategic targets & score math

  • Score granularity: 1 test output on 120 semi-private tasks ≈ 0.5–1.0pp depending on outputs-per-task mix. RECOMMENDATION: treat all LB moves < 2pp as unproven.
  • Internal milestones RECOMMENDATION: M-A: local harness parity (G0) → M-B: beat open public baseline on held-out train split → M-C: ≥ 24% equivalent on public eval/local proxy (2025 SOTA) → M-D: public LB ≥ 40% (top-10 plausible) → M-E: top-8/top-3 push via ensemble + selection tuning.
  • Where our edge can come from (weaknesses of common approaches, from postmortems & LB structure — OBSERVATION): ① selection is usually heuristic (top-vote) while pass@2 rewards a calibrated 2-attempt policy; ② ensembles are often near-duplicates (same family, different seeds) — low diversity, low ceiling; ③ runtime is poorly budgeted — many submissions starve their hardest tasks; ④ public-eval overfitting — teams tune on the 120 public tasks and lose the semi/private delta; ⑤ AGI-2 capability axes (symbolic/compositional/contextual) are under-served by generic RE-ARC-style data.

C2-E01 Scorer parity & harness P0open ▾
Question: can I trust every number my harness produces?
Hypothesis
A local scorer implementing "best-of-2 exact match per test output, averaged over outputs" can match Kaggle scoring with zero discrepancy.
Why improve
Not a score lever directly — it is the precondition for every delta we ever report; mis-scoring invalidates all decisions.
Implementation
Loader for ARC JSON (train/public eval); scorer with multi-output tasks + both attempts; validator enforcing the official submission schema (all task_ids present, attempt keys, output ordering); unit tests with hand-built edge cases (single-output, multi-output, wrong shapes, duplicate attempts).
Expected signal
100% unit-test pass; scorer output = 1.0 on perfect predictions, 0.0 on all-zeros; manual re-grade of 20 random tasks agrees with scorer.
Validation
Score the public eval set against its published ground truth in-harness; verify JSON validator rejects each malformed fixture.
Failure condition
Any discrepancy between scorer and manual/official reference; ambiguity in multi-output handling.
Decision rule
No other C2 work proceeds until PASS. If ambiguity remains → resolve via Rules/Discussion tab before building anything else.
C2-E02 Submission pipeline validation P0open ▾
Question: does a notebook survive the real Kaggle path (commit → submit → score → runtime measured)?
Hypothesis
A trivial submission (all-zeros, then prior-copy) completes the Kaggle loop and returns a score consistent with the harness.
Why improve
Format/runtime bugs discovered in week 6 cost a week; discovered now they cost an hour. Also measures real evaluation latency.
Implementation
Notebook A: all-zeros submission.json; Notebook B: "copy most-frequent train output shape" heuristic; both from the same repo template with config snapshotting.
Expected signal
Both scored; all-zeros ≈ 0; B0-small ≥ 0; runtime telemetry recorded; submission ledger entries created.
Validation
Kaggle score vs harness prediction of the same artifacts (should match exactly).
Failure condition
Submission rejected / runtime exceeded / score inconsistent with harness.
Decision rule
Keep template that passed; log all timings in ledger; if rejected → fix format issues immediately (this is a bug, not an experiment).

Question: what number defines "better" for all future deltas?
Hypothesis
A public open system (TRM inference and/or 2024/2025 open TTT notebook), run at reduced scale locally, yields a stable reference score on V.
Why improve
All keep/kill decisions are relative to B0; without it, "improvement" is opinion.

C2-E04 Pass@k ceiling of local program synthesis P0open ▾
Question: how much headroom does candidate generation hold, and where should compute go?
Hypothesis
An open code/CoT model executed locally, prompted per-task with demonstrations + executed-verification loop, shows a steep pass@1 ≪ pass@8 gap on V.
Why improve
Pass@k gap quantifies selection headroom (feeds E07) and generation quality ceiling (feeds E06); it converts "LLMs might help" into a number.
Implementation
Local weights (bundled later for submission); per task: sample k=8–16 candidate Python/DSL programs with temperature ladder; execute against demonstration pairs; keep executables fitting all demos; record per-task pass@k curves + failure buckets (no-program, wrong-shape, wrong-rule).
Expected signal
pass@8 − pass@2 ≥ 5–10pp → selection is the bottleneck; pass@2 ≈ pass@8 → generation is the bottleneck.
Validation
Same 100 V tasks, fixed seeds, 2 repeats; error buckets tabulated.
Failure condition
pass@2 near 0 across prompts/models → local model priors too weak; pivot weight to TTT (E05) and data (E06).
Decision rule
Keep as generator if pass@2 ≥ B0/2; invest in E07 if pass@8 ≫ pass@2; modify prompts/model choice once; then freeze.
C2-E05 TTT + augmentation voting strong baseline P0open ▾
Question: does the proven 2024/25 recipe (per-task test-time training + voting) beat our generation-only baseline?
Hypothesis
Per-task fine-tuning on 8 dihedral × color-permutation augmented demonstrations, selecting checkpoints by train fit, and voting outputs across augmentations lifts V score ≥ 5pp over E04-only.
Why improve
TTT specializes priors to each task's rule family; augmentation voting cancels orientation/color noise — the single most replicated win in ARC history.
Implementation
Augmentation lib (verified: 8 dihedral transforms; color-perm sampling); per-task LoRA/full fine-tune with early stop on demo-fit; vote across augmentations with confidence = agreement count; produce 2 attempts = top-2 distinct outputs by vote.
Expected signal
V: Δ ≥ +5pp vs B0; runtime ≤ budget with E10 headroom.
Validation
Paired vs B0 on V; ablate voting off (E11 feeds); 2 seeds.
Failure condition
Δ < +2pp after two tuning iterations, or runtime blows past budget with no fix.
Decision rule
Keep if Δ ≥ +5pp; modify (checkpoint-selection rule, aug set) once if +2–5pp; discard below +2pp and reallocate to E06/E07.
C2-E06 Capability-targeted synthetic data P1open ▾
Question: does pretraining on generators built for AGI-2's three axes (symbolic / compositional / contextual) transfer better than generic ARC-like data?
Hypothesis
A mix of {RE-ARC-style volume + axis-targeted generators} as pretraining/fine-tuning corpus raises V score ≥ 3pp over generic-only, with largest gains on the error buckets tagged symbolic/compositional/contextual.
Why improve
AGI-2 was built to break pattern-matchers; targeted synthetic data is the cheapest way to inject those rule families into priors (NVARC's cited edge).
Implementation
Generator families: (a) symbol→semantics mappings, (b) multi-rule conjunction tasks, (c) context-conditioned rules; verify generator outputs are human-plausible via spot-checks; pretrain base model → rerun E05 pipeline unchanged.
Expected signal
Δ ≥ +3pp overall AND disproportionate gain on the three tagged buckets (error-bucket table before/after).
Validation
Same V; ablate corpus mix (generic vs targeted vs both); 2 seeds.
Failure condition
No Δ, or Δ only on tasks already solved (no bucket shift).
Decision rule
Keep mix that wins; modify generator distributions once if buckets don't move; discard targeted data if it hurts general buckets (catastrophic interference).
C2-E07 Selection & 2-attempt policy P1open ▾
Question: how close to the pass@8 oracle can a calibrated 2-attempt selector get?
Hypothesis
Ranking candidates by a feature vector (train-fit, augmentation-agreement, execution-consistency, program simplicity/MDL, generator identity) recovers ≥ 50% of the pass@8−pass@2 gap.
Why improve
Pass@2 makes the top-2 picks the entire product; every pp of selection = pp of leaderboard, independent of generation quality.
Implementation
Log all candidates + features on V; offline: sweep ranking rules (weighted score, learned pairwise ranker if data suffices); attempt_1 = argmax, attempt_2 = best diverse runner-up (penalize near-duplicates of attempt_1).
Expected signal
Selected-2 accuracy ≥ midpoint between naive top-vote and oracle; ablation shows each feature's marginal value.
Validation
Held-out fold of V untouched by feature tuning; report gap-closure %; 5-fold CV for the learned variant.
Failure condition
Learned ranker overfits V folds (CV variance high) → fall back to fixed heuristic weights.
Decision rule
Keep best selector; freeze weights before any public-eval run; re-evaluate only inside E11 ablation.
C2-E08 Heterogeneous ensemble & leave-one-out P1open ▾
Question: does every family in the ensemble earn its runtime?
Hypothesis
Union-voting across ≥3 families (TTT net, TRM-class, program-search; optional MDL) beats the best single family by ≥ 3pp, and each family contributes unique solves (leave-one-family-out Δ > 0 for all).
Why improve
Families make uncorrelated errors (NVARC's verified pattern); union converts "different failure modes" into new solves.
Implementation
Per task: collect candidate outputs from all families; score by calibrated agreement + family reliability weights; attempts = top-2 distinct by ensemble score; track per-family solve matrices.
Expected signal
Ensemble Δ ≥ +3pp over best solo; solve-overlap matrix shows < 80% overlap between family solve-sets.
Validation
Paired on V; runtime accounting per family (feeds E10).
Failure condition
Any family with LOO Δ ≈ 0 while consuming > 15% runtime.
Decision rule
Keep families with positive LOO Δ per runtime-pp; discard/limit (e.g., run on 20% hardest tasks only) the rest.
C2-E09 Execution-verified evolutionary search P2open ▾
Question: does SOAR-style search add solves on tasks the samplers miss?
Hypothesis
Evolutionary mutation of LLM-proposed programs with execution-verified fitness solves a distinct slice of V tasks (≥ +1.5pp) at bounded GPU cost.
Why improve
Search converts compute into exactness on tasks where one-shot sampling plateaus; verified traces could later fine-tune generators (SOAR pattern).
Implementation
Population per task from E04; mutation ops (edit lines, swap ops, retarget colors); fitness = demos fit count then MDL tie-break; budget-capped generations; stop on perfect fit.
Expected signal
Δ ≥ +1.5pp concentrated on tasks unsolved by E04/E05; cost per extra solve documented (GPU-hr/pp).
Validation
Paired on V with fixed budget; report marginal solve cost curve.
Failure condition
Cost per extra solve > 2× the same budget spent on more sampling (E04 curve).
Decision rule
Keep if beats sampling-per-pp; restrict to hardest-tier tasks if only they benefit; else discard.
C2-E10 Runtime budget engineering P2open ▾
Question: can the full pipeline fit 12h with ≥ 30 min margin, and does reallocation add solves?
Hypothesis
Profiling + early-exit on solved tasks + difficulty triage (easy tasks get small k, hard tasks get the savings) yields ≥ +1pp within identical runtime.
Why improve
12h is a hard constraint; wasted minutes on already-solved tasks are the cheapest source of new compute; ±10 min runtime obfuscation demands margin.
Implementation
Phase timer; solved-detector (train-fit perfect + consistent vote) triggers skip; triage tiers by cheap first-pass difficulty estimate; batch scheduling; cache augmentation results.
Expected signal
Wall-clock ≤ 11.5h on full local replay; Δ ≥ +1pp from reallocation on V.
Validation
Full-pipeline dry run ×2 (variance ≤ 10 min); paired V score before/after triage.
Failure condition
Replay > 12h or triage misclassifies hard tasks as easy (solved-count drop).
Decision rule
Keep settings that pass margin test; re-tune tiers once if triage error > 5%; else simplify to uniform budget.
C2-E11 Component ablation table P1open ▾
Question: what is the measured contribution of every component (required for paper + final decisions)?
Hypothesis
Each major component (TTT, voting, synthetic pretraining, selection, each ensemble family, triage) shows Δ > 0 in leave-one-component-out on V.
Why improve
Ablations are simultaneously: final-system pruning, the paper's key table, and the audit trail against self-deception.
Implementation
Fixed final config; matrix of −component runs on V; identical seeds; one shared results table in the ledger with Δ + CI per row.
Expected signal
No component with Δ ≤ 0 remains in the final config; paper Table 1 materializes.
Validation
2 seeds per row for rows with Δ < 2pp.
Failure condition
Any component negative or flat.
Decision rule

6.3Where score comes from (first principles, interactive edition)

Total = mean over games of level-weighted level-scores. A game scores 0 until its first level is completed — completion dominates; the squared efficiency term only matters after completion. Therefore the doctrine is:

PrincipleDerived fromMechanism
1. Completion before efficiencymin(h/a,1)² is 0 with no completionNever trade a completion chance for action frugality; optimize actions only within a solved level's replay, or when actions do not risk progress.
2. Early levels carry the gamelevel-index weighting (1-indexed)Later levels weigh more, but are unreachable without early ones; secure level 1–2 reliably before investing in depth strategies.
3. Actions are the budgetefficiency term + 9h wall-clockEvery action must buy information (exploration value) or progress (goal value); a default policy of "cheap probes, expensive commitments".
4. Memory is compound interestmulti-level games, RESET availabilityKnowledge of action semantics learned at level k must persist to level k+1 and across RESETs — relearning is pure efficiency loss.
5. Determinism is a hypothesis to testgames are rule-basedSame action, same context ⇒ same effect (verify, don't assume); non-determinism detected early prevents wasted planning.

C3-E02 Baseline agent ladder P0open ▾

Implementation

C3-E03 Structured state representation P1open ▾

Hypothesis

Why improve

Implementation

Expected signal

Validation

Failure condition

Decision rule

C3-E04 Exploration policy comparison P1open ▾
Question: which policy converts actions into information fastest?
Hypothesis

Why improve
Information gain per action is the currency of the efficiency term; probing converts blind search into hypothesis testing.
Implementation

Validation

Failure condition

Keep best policy overall; consider budget-conditional policy (probe early, exploit late) as the modified winner.
C3-E05 Persistent action-semantics memory P1open ▾
Question: does remembering action semantics across levels/RESETs compound into score?
Hypothesis
A per-game persistent store (context signature → action → predicted effect + confidence + counter-evidence) that survives level transitions and RESETs reduces actions-to-reach-level-k and lifts late-level progress.
Why improve
Games are multi-level with consistent engine semantics; relearning is pure efficiency loss and the squared term + level weighting amplify it.
Implementation

Expected signal
Actions-to-level-2/3 ↓ vs no-memory control on multi-level games; memory hit-rate (predictions confirmed) > 70%.
Validation

Failure condition

Decision rule

Failure condition

C3-E08 Efficiency farming (post-completion) P2open ▾

Failure condition

Validation

Failure condition

Decision rule

9.4Where competition evidence is NOT enough (gaps to close for publication)

  • External validity: private-LB scores alone are not a research result. Required: public-eval + held-out-train results with CIs, and (for the C3 half) results across all 25 public games, not cherry-picked ones. → covered by our validation doctrine (§3.5, §6.4).
  • Baselines at matched compute: reviewers will ask "more compute would also help". Required: equal-runtime comparisons (E09's cost curves, E08's per-runtime-pp accounting) — already in our protocol.
  • Generality: at least one out-of-distribution probe: run the C2 selector on ARC-AGI-1 public tasks (or ConceptARC) and the C3 agent on its held-out games; report honest transfer. → add as P2 experiments in W5–W6 (C2-X1, C3-X2 in ledger).
  • Mechanistic depth: rubric Theory requires "why it works". Required: error-bucket analysis linking each component to specific failure classes it fixes — the E06/E07 bucket machinery provides this.
  • Novelty positioning: related-work delta vs TTT (Akyürek), Product-of-Experts (Franzen et al.), TRM, SOAR, programmatic world models (arXiv 2607.28287) must be explicit. → §10.3.
